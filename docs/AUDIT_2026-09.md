## 1. 🔴 Blokery – opravit před 1.0

### 1.1 `capture_tokens` a `draft_capture_photos` nemají zapnuté RLS

- **Kde:** `supabase/migrations/20260228000000_capture_tokens.sql`,
  `supabase/migrations/20260230100000_capture_draft_tokens.sql`
- **Problém:** Ani jedna migrace neobsahuje `ENABLE ROW LEVEL SECURITY` ani jedinou policy.
  Ve výchozím nastavení Supabase mají role `anon` a `authenticated` granty na tabulky
  ve schématu `public`. Anon klíč je přitom vestavěný jak v desktop aplikaci, tak
  ve veřejné capture stránce (`capture/capture.js`) – tedy volně dostupný.
- **Dopad:** Kdokoli s anon klíčem může číst platné capture tokeny (platnost 15 min)
  a nahrát fotky do cizí zakázky, případně číst URL fotek z `draft_capture_photos`.
- **Oprava je bezpečná a triviální:** obě tabulky se v celém kódu čtou i zapisují
  **výhradně přes `service_role`** v edge funkcích (`capture-create-token`,
  `capture-upload`, `capture-list-draft`, `capture-claim-draft`). Service role RLS obchází,
  takže stačí RLS zapnout a **nepsat žádnou policy** – funkčnost zůstane nedotčená
  a pro `anon`/`authenticated` se tabulky uzavřou.

```sql
-- nová migrace
ALTER TABLE public.capture_tokens ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.draft_capture_photos ENABLE ROW LEVEL SECURITY;
```

**Ověření před opravou** (v SQL editoru Supabase):

```sql
SELECT relname, relrowsecurity FROM pg_class
WHERE relname IN ('capture_tokens','draft_capture_photos');

SELECT grantee, privilege_type FROM information_schema.role_table_grants
WHERE table_name = 'capture_tokens' AND grantee IN ('anon','authenticated');
```

### 1.2 Bezpečnostní tokeny se generují přes `Math.random()`

- **Kde:**
  - `supabase/functions/password-reset-request/index.ts:13` – **12 znaků**
  - `supabase/functions/invite_create/index.ts:14` – 32 znaků
  - `supabase/functions/capture-create-token/index.ts:24` – 32 znaků
- **Problém:** `Math.random()` je v V8 xorshift128+ – **není kryptograficky bezpečný**.
  Vnitřní stav má jen 128 bitů a lze ho rekonstruovat z pozorovaných výstupů.
  Útočník, který si nechá vygenerovat několik vlastních tokenů, může předpovědět
  token vydaný oběti.
- **Dopad:** Nejzávažnější u **resetu hesla** – předpovězený token = převzetí účtu.
  Token má navíc jen 12 znaků a platnost 60 minut.
- **Poznámka:** Tento nález byl už v `AUDIT_AUTH_DB_CONNECTIONS.md` (bod 3, únor 2026)
  a **stále není opraven**. Zbylé dva nálezy z toho auditu opravené jsou.
- **Oprava** – ve všech třech funkcích nahradit generátor:

```ts
function generateToken(len = 32): string {
  const chars = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_";
  const bytes = new Uint8Array(len);
  crypto.getRandomValues(bytes);              // Deno má crypto globálně
  return Array.from(bytes, (b) => chars[b % chars.length]).join("");
}
```

U resetu hesla zároveň zvýšit délku z 12 na aspoň 24 znaků.

### 1.3 Žádný rate limiting na `password-reset-request`

- **Kde:** `supabase/functions/password-reset-request/index.ts`
- **Problém:** Funkce po přijetí e-mailu rovnou vloží nový token do
  `password_reset_tokens` bez jakéhokoli omezení počtu pokusů.
  (Staré tokeny se mažou – vždy je platný jen jeden – to je v pořádku.)
- **Dopad:** Umožňuje spamovat e-mailovou schránku uživatele. V kombinaci
  s bodem 1.2 (predikovatelný token) je to horší: útočník si může nechat
  vygenerovat libovolné množství vzorků pro rekonstrukci PRNG.
- **Oprava:** Před insertem zkontrolovat počet tokenů pro daný e-mail za posledních
  15 minut, staré tokeny mazat, a při překročení limitu vrátit stejnou odpověď
  jako při úspěchu (aby nešlo enumerovat existující účty).

### 1.4 `npm run build` neprojde – 9 lint errors

`build` = `typecheck && lint && vite build`. Typecheck projde, lint spadne.
(`build:prod`, který používá `tauri:build`, lint přeskakuje – release tedy technicky
projde, ale build skript je rozbitý.)

| Soubor | Pravidlo | Reálné riziko |
|--------|----------|---------------|
| `src/components/Toast.tsx:191` | `react-hooks/purity` – `Date.now()` v renderu | Nízké (jen initial value `useRef`), ale React Compiler kvůli tomu komponentu neoptimalizuje |
| `src/hooks/useGlobalSmsUnreadCount.ts:30,32` | `react-hooks/refs` – zápis do refu během renderu | Nízké, ale je to v **novém, necommitnutém SMS kódu** – opravit dřív, než se zamrazí |
| `src/lib/devicesDb.ts:171,188,205,227` | `no-constant-binary-expression` | Mrtvý kód – `String(error) ?? "..."` se nikdy nepoužije |
| `src/lib/achievements.ts:117`, `src/pages/SmsChatsPage.tsx:132` | `prefer-const` | Kosmetika |

Fix: refy nastavovat v `useEffect` (nebo přes `useEffectEvent`), `Date.now()` do
lazy initializeru `useRef(() => …)` / `useState`, zbytek `eslint --fix` + ruční úprava.

  2. **iOS odložit** za 1.0 a zmrazit ho, aby nekonzumoval čas.
  3. **iOS zrušit** a nahradit responzivním webem (`web/` už existuje).

### 2.2 Testy pokrývají jen pomocné funkce

- 7 testovacích souborů, 61 testů – všechny nad `src/lib/*` a `src/utils/*`
  (normalizace chyb, telefon, barvy statusů, dokumenty).
- **Nulové pokrytí:** stránky, komponenty, DB vrstva, **všech 24 edge funkcí**,
  RLS policies, auth flow, capabilities.
- `src/pages/Orders.tsx` má **9 454 řádků** a nula testů.
- **Minimum pro 1.0:** testy na auth a role (owner/admin/member + capabilities),
  na edge funkce kolem pozvánek a resetu hesla, a integrační test RLS
  (uživatel ze servisu A nesmí vidět data servisu B).

### 2.3 Žádná CI

- Chybí `.github/` úplně. Typecheck, lint a testy se spouští jen ručně –
  což je právě důvod, proč lint půl roku hnije s 9 errory.
- **Fix:** jednoduchý GitHub Actions workflow na push/PR:
  `npm ci && npm run typecheck && npm run lint && npm run test:run`.

### 2.4 Žádný crash reporting

- V `src/main.tsx` je `ErrorBoundary` (dobře), ale chyba se nikam neodesílá.
  Když appce spadne u zákazníka, nedozvíš se to.
- **Fix:** Sentry (má Tauri/Rust i JS SDK) nebo aspoň zápis chyb do Supabase tabulky
  z `ErrorBoundary.componentDidCatch`.

### 2.5 Zranitelnost v závislosti `ws` (high)

- `npm audit`: `ws@8.0.0–8.20.1` – uninitialized memory disclosure + memory exhaustion DoS.
- **Fix:** `npm audit fix`.
- Zároveň je zastaralých ~20 balíčků, mj. `@supabase/supabase-js` 2.89 → 2.113
  a všechny Tauri pluginy. Aktualizovat ve vlastním commitu, s otestováním.

## 6b. Nálezy zjištěné až při zprovozňování (2. 9. 2026)

Tyhle věci statický audit neodhalil – vyplavaly, až když se projekt reálně spouštěl a builil.

### 6b.1 🔴 JobiDocs: 8 zranitelností v produkčních závislostech

`npm audit --omit=dev` v `jobidocs/` hlásil **8 nálezů (7 high, 1 moderate)** –
mimo jiné **`fastify`** a **`find-my-way`**, tedy přímo HTTP server, který JobiDocs
vystavuje na portu 3847, dále **`electron-updater`**, **`ws`** a **`js-yaml`**.
Na rozdíl od hlavní appky se tohle uživatelům skutečně dodává.

Celkem (včetně dev) jich bylo **42** (3 critical, 33 high).

**Opraveno:** `npm audit fix` – produkční nálezy **8 → 0**, celkem **42 → 15**.
`package.json` se neměnil (šlo o tranzitivní závislosti), build ověřen a projde.
Zbylých 15 je dev-only a vyžaduje breaking changes (`concurrently`/`shell-quote`,
`tar`, řetěz kolem `@babel/core`).

**Zůstává k rozhodnutí:** Electron je na **33.4.11** (`^33.0.0`). Aktuální řady jsou
výš; upgrade je breaking a chce vlastní testování tisku.

### 6b.2 🟠 Rozbitá build cache s cestou z jiného umístění

`cargo check` padal na `failed to read plugin permissions: …/permissions/app/autogenerated/commands/app_hide.toml`.
Cesta v chybě zněla `/Volumes/backup/jobi/…` – **bez druhého `backup`**. Projekt byl
někdy přesunutý nebo obnovený ze zálohy na jinou cestu a 14GB `src-tauri/target`
zůstala navázaná na tu starou.

**Opraveno:** smazán `src-tauri/target/debug/build` (1,2 GB, regenerovatelné).
`cargo check` pak projde za 34 s.

### 6b.3 🟡 Verze byla rozjetá i v Cargo.toml

V kapitole 3.1 je uvedený jen `package.json`. Ve skutečnosti byl rozjetý i
`src-tauri/Cargo.toml` – **0.1.2**, zatímco `tauri.conf.json`, `package.json`
i JobiDocs měly 0.2.3. `set-version.sh` sice Cargo.toml aktualizuje, ale
u posledních releasů zjevně neproběhl.

**Opraveno:** Cargo.toml srovnán na 0.2.3.

### K čemu je rozdělení dobré

Tři důvody, seřazené podle toho, jak jsou doložené:

1. **Překreslování.** Každá z 63 změn stavu překreslí celý strom o 6 457
   řádcích. Napsání písmene do vyhledávání přepočítá i seznam zakázek
   a modal. Stejná třída problému jako rozostření, které dnes způsobovalo
   trhání na Windows.
2. **Souběžná práce.** Ověřeno prakticky – dvě relace pracující ve stejném
   stromě si opakovaně vlezly do stejných souborů, `App.tsx` byl chvíli
   v nefunkčním stavu.
3. **Změna na jednom místě.** Doloženo dnešní prací: po vytažení sdílených
   prvků karty se zhuštění seznamu dělalo jednou místo devětkrát. Právě
   opakování stejného kódu vyrobilo těch 19 velikostí písma.

### Proti čemu to vážit

Rozdělení **samo o sobě neopraví žádnou chybu** a aplikace funguje. Nese
riziko regresí – u 6 457 řádků s 63 stavy se snadno něco tiše rozbije.
A když se udělá špatně, tedy jen rozseká soubor bez řešení hranic
překreslování, zbydou jen další soubory a stejný výkon.

**Doporučení:** nedělat proto, že je to „správně". Dělat tehdy, když pálí
výkon nebo souběžná práce. A rozhodně ne jedním řezem – postupně (modal
detailu, seznam, filtry), s ověřením po každém kroku. Každý krok je sám
o sobě přínos a dá se kdykoli zastavit.
